# CS320 Software Testing, Automation QA

To make sure my code is functional and secure, I actually test it, and try to identify all of the weird edge cases instead of assuming it works. In this course I wrote JUnit tests for every requirement, checking both good and bad input, and used coverage reports to find what I missed. For security, I validate all input before it's stored. To interpret user needs, I turn each requirement into something I can actually test. For example, if a requirement says a phone number has to be exactly 10 digits, that becomes a validation check and a test that tries 9 digits, letters, and null. When designing software, I break it down into smaller pieces instead of just one whole confusing piece, because if you're trying to do everything at once, you'll get lost, the functionality will break, and it'll be a mess you'll be in a rush to clean up before it hits production. For example, I used an object class that handles its own validation and a service class that manages adding, updating, and deleting. I build one requirement at a time, test it, ensure it works, then move onto the next. I also further explained this in my Project Two reflection.
